# NexiMail V1.2 Adversarial QA Audit

Date: 2026-09-24
Branch: codex/v1.2-hardening
Repository: manshu145/Mail
PR: #11

## Objective

Audit V1.2 as a hostile production tester rather than a feature reviewer, with the four acceptance priorities:

1. Customer campaigns must not fail or become mysteriously stuck because of individual bad recipients or isolated provider problems.
2. Production has no artificial recipient/day/hour platform cap; safety comes from validation, reputation controls, pacing, and backpressure.
3. Campaign operation should remain understandable and actionable for customers.
4. Reporting must be internally consistent and resilient to tracking anomalies.

Absolute inbox placement cannot be guaranteed by application code because recipient providers decide final filtering. The application acceptance target is that NexiMail does not create avoidable spam/reputation failures and that all safety actions are explicit, recoverable, and auditable.

## Automated adversarial matrix

The branch contains 300 deterministic adversarial cases in `tests/v12-adversarial-300.test.ts`, covering:

- validation positive/negative/inconclusive states and Gmail RCPT boundaries
- provider mapping across Gmail/Yahoo/Microsoft/Proton/Rediff/Zoho/custom domains
- provider-vs-upstream restriction classification including JFE050007
- recipient hard-bounce vs policy vs temporary-failure suppression
- adaptive delivery at 20/94/99/100/101/300/301/600/601/5000 recipients
- bounce-stop and warning-rate boundaries
- open/click qualification before delivery, scanner detection, proxy behavior and shared-IP bursts
- content safety boundaries for missing content, script URLs, shortened URLs, dangerous files and mismatched destinations

The CI run immediately before the later fixes reported 398 total tests with 398 passing and 0 failing.

## P0/P1 defects found and corrected on the branch

### 1. Inconclusive mailbox validation was sendable
Problem: `validationAllowsSend()` accepted `unknown` and `error` states.
Impact: an inconclusive mailbox could enter transport and increase hard-failure/reputation risk.
Fix: only `accepted` and `valid` states are send-eligible; SQL audience selection matches this rule.

### 2. A mixed audience could be blocked by unsafe recipients
Problem: the launch guard treated pending validation as campaign-blocking even when safe recipients existed.
Impact: customer irritation and unnecessary full-campaign stoppage.
Fix: unsafe/pending recipients are held; eligible recipients can continue. A campaign blocks only when no eligible recipient remains or a true campaign-wide safety condition exists.

### 3. Recipient-domain health could leak non-valid domains into sending
Problem: only `no_mx`/`null_mx` were excluded in SQL, while missing/errored domain-health records could still appear send-eligible.
Fix: send eligibility now requires a present, `valid` domain-health record.

### 4. Policy/reputation bounces could become recipient suppressions
Problem: postfix bounce handling wrote every bounce into suppression, including policy/reputation rejections.
Impact: legitimate recipients could be permanently suppressed due to a sender/content problem rather than mailbox invalidity.
Fix: suppression is now created only when bounce classification explicitly confirms recipient-not-found/hard-bounce evidence. Backfill logic was hardened the same way.

### 5. Engagement could be counted before delivery
Problem: open/click qualification could treat activity as qualified before the message had confirmed delivery.
Impact: distorted open/click reporting and possible rate anomalies.
Fix: open/click qualification fails closed until delivery is confirmed.

### 6. Live click tracking did not apply shared-IP qualification
Problem: the first implementation of live click tracking supplied a constant shared-IP count of 1.
Fix: the route now evaluates recent click events for the same hashed IP before applying click qualification.

### 7. Reputation worker could globally pause a sender account
Problem: the reputation worker directly changed `sending_accounts.status` to `paused` when aggregate thresholds were crossed.
Impact: one sender-level metric could globally interrupt all campaigns and create customer-visible sender failures.
Fix: reputation worker is now telemetry-only. Campaign-level adaptive safety and explicit provider/upstream cooldowns remain the enforcement mechanisms.

## Safety behavior now expected

### Per-recipient
- invalid/hard-bounce recipients -> suppression
- unsubscribed/complaint/suppressed recipients -> never sent
- inconclusive validation -> held, not sent
- recipient mailbox-full/temporary condition -> remains in MTA retry path without global provider pause

### Per-provider
- provider-specific throttling/restriction -> provider lane cooldown
- unrelated providers continue
- controlled probe clears the provider lane after recovery

### Shared outbound path
- JFE050004/JFE050005/JFE050007 or explicit account/outbound suspension -> upstream cooldown
- shared path is not represented as fake independent provider cards
- launch is blocked while the genuinely shared path is unavailable

### Campaign safety
- first canary is released conservatively
- bounce warning slows the next release
- dangerous early bounce rate pauses the campaign
- campaign state remains resumable instead of converting unsent recipients into failed delivery
- transport re-checks suppression/validation/consent immediately before MTA submission

### Reporting
- open/click metrics use qualified events
- engagement before confirmed delivery is excluded
- campaign metrics keep terminal delivery, pending delivery and engagement counters separate
- campaign/provider drill-downs expose actual recipient outcomes and cooldown impact

## Remaining production-certification items

These are not silently marked passed:

1. **Live 5k/10k campaign certification cannot be declared while the certification VPS continues to receive live JFE050007 responses from destination MX tests.** Code can prevent avoidable retries and isolate lanes, but it cannot manufacture a clean upstream reputation path.
2. **Transport pacing is conservative but not a fully adaptive rate controller.** Current dynamic behavior is strongest in canary/release progression and provider cooldowns; message-per-second is still primarily configuration-driven.
3. **Inbox-placement measurement is not a proof of inbox delivery.** The repository contains inbox/seed database structures, but there is no complete end-user seed-test workflow in the current branch tree.
4. **Campaign concurrency/backpressure settings are scheduler controls, not recipient limits, but their UX should continue to be presented as background safety rather than a hidden product quota.**

## Release gate

Do not merge PR #11, tag V1.2, or roll customers until:

- current branch CI is green
- the adversarial matrix remains green after the final changes
- live certification path is clean enough to run controlled sends
- controlled 1k, 2k, 5k and 10k campaigns are observed
- at least three campaign runs are completed as previously planned
- no duplicate delivery, retry-storm, suppression bypass, false completion, or reporting integrity anomaly is observed
